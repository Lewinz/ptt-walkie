# 需求与产品设计

## 原始诉求

> 做一个面向司机（但不限于）的灵矽应用：语音对讲机。可以通过各种灵活手段建群（不限于通过语音，请设计合理的产品逻辑），然后通过嵌入式设备进行群语音对讲。支持语音切换群（房间）。

平台：七牛云 [灵矽 AI](https://xrobo.qiniu.com/#/agent-market)。

## 背景：灵矽是什么

灵矽 AI 是七牛云 2025-08 发布的智能硬件语音交互平台：

- **语音对话底座**：ASR → LLM → TTS 全链路（宣称端到端 <600ms、打断 <300ms），支持声音克隆。
- **多模型切换**：DeepSeek、通义千问、豆包、智谱等。
- **MCP 能力扩展**：通过云端 MCP 模块给智能体加技能（智能体市场），无需改固件。
- **硬件载体**：官方 ESP32-S3 语音机芯盒，另适配乐鑫、亮牛、国芯微等芯片，配套 SDK。

> 推测（待确认）：控制台「智控台」+ ESP32-S3 + MCP 的组合与开源 [xiaozhi-esp32](https://github.com/78/xiaozhi-esp32) 生态高度相似，可能复用其协议体系。

**关键认知**：灵矽解决的是「人 ↔ AI 对话」，本项目要做的是「人 ↔ 人对讲」。智能体链路（ASR→LLM→TTS）不适合承载实时群语音转发：延迟高、丢原声、无法向其他设备主动推流。

## 核心架构：控制面 / 语音面分离

```
            ┌─────────────── 控制面（灵矽负责）──────────────┐
  "切到车队群" → 灵矽智能体（ASR+LLM） → 本项目 MCP Server → 群组后端
            └──────────────────────────────────────────────┘
                                              │ 下发"切换频道"指令
            ┌─────────────── 语音面（自建）──────────────────┐
  按住PTT讲话 → Opus 音频流 → 对讲转发服务 → 群内其他设备直接播放
            └──────────────────────────────────────────────┘
```

| 层 | 职责 | 技术 |
|---|---|---|
| 控制面 | 建群、入群、切群、查成员、邀请、回放、摘要 | 灵矽智能体 + 自研 MCP Server |
| 语音面 | 实时群对讲：抢麦、转发、播放、录音存档 | 自建转发服务，Opus，WebSocket 或 MQTT+UDP |
| 管理面 | 扫码建群、车队管理、成员审批 | 小程序 / H5，与后端共用 API |

## 产品设计

### 建群方式

| 方式 | 场景 | 交互 |
|---|---|---|
| 语音建群 | 司机临时组队 | "建个群叫京沪线车队" → 播报"已创建，房间号 3721" |
| 房间号口令 | 电话里或当面口头告知 | "加入房间 3721"（短号，避开易混淆数字） |
| 附近建群 | 服务区、货场、堵车 | "附近有什么群" / "建一个附近的群"，GPS 范围 + 时间窗口 |
| 同路线群 | 跑同一条线 | 按目的地或高速路段推荐，司机确认后加入 |
| 扫码 / 分享 | 车队长组织 | 小程序生成二维码或链接，扫码绑定设备入群 |
| 碰一碰（可选） | 两台设备挨着 | NFC 或同时按键配对 |
| 批量导入 | 物流、网约车公司 | 后台导入设备列表，设固定频道 |

群分两类：**临时群**（附近群、路线群，长时间无人发言自动解散）和**固定群**（车队群、老乡群）。

### 语音切群

- 按名字："切到老乡群"、"去车队那个"（LLM 模糊匹配）。
- 按顺序："下一个频道" / "上一个"，也可用物理旋钮。
- 按房间号："切到 3721"。
- 查询："我在哪个群"、"群里有谁在线"。
- 切换后短 TTS 确认："已切换到老乡群，5 人在线"。

### 司机安全与体验

- **PTT 优先**：物理大按键或方向盘按键说话，不依赖唤醒词；VOX 声控发射仅作可选。
- **音频优先级**：对讲语音打断 AI 播报；紧急频道和车队长消息优先级最高。
- **抢麦机制**：同一时刻一个群只允许一人发言，服务端加锁；抢不到时用提示音而非语音。
- **回放**："刚才说的再放一遍"、"刚才是谁说的"。发言存档于七牛 Kodo。
- **AI 摘要**："我错过了什么" → 错过时段的语音转文字后由 LLM 总结。
- **关键词预警**：转写中出现"事故、查车、封路"等词时，先放提示音再播放。
- **静默与勿扰**："这个群先静音"、"只听车队长的"。
- **离线补收**：隧道、山区断网后重连，自动补播或先播摘要。

### 场景扩展（不限于司机）

骑行 / 登山队伍、景区导游、工地 / 仓库班组、家庭（老人和孩子的设备）。按场景做群模板，预设不同的 TTS 话术与优先级规则。

## MCP 工具设计（草案）

```
create_group(name, type=temp|fixed, visibility=code|nearby|route) → {group_id, code}
join_group(code | name | group_id)
switch_group(query)        # LLM 传模糊名，后端匹配
list_my_groups()
list_nearby_groups(radius_km)
get_group_status()         # 当前群、在线人数、谁在说话
leave_group(group_id)
mute_group(group_id, minutes)
replay_last(n=1)
summarize_missed(since)
invite(contact | plate_no) # 可选
```

前提：MCP 工具被调用时必须能拿到发起设备的身份（device_id / 用户），否则无法确定"我"是谁。

## 实现路径

### 第 0 步：确认平台能力（决定走路线 A 还是 B）

- [ ] 能否刷自定义固件 / OTA？设备能否在灵矽连接之外再建一条对讲连接？
- [ ] MCP 调用是否携带设备 ID？
- [ ] 服务端能否主动向设备推送消息或音频（设备端 MCP、通知等）？
- [ ] 硬件是否有 4G（车载 WiFi 不可靠，需 4G Cat.1）及可用作 PTT 的按键？

### 路线 A：仅 MCP，不改固件（验证用）

"语音留言群"：用户说"给车队群发：前面堵车" → ASR 转文字 → MCP 存群消息；其他人询问时 TTS 读出。约一周可做完，能验证建群 / 切群交互，但**不是实时对讲**，无原声、无主动推送。

### 路线 B：自定义固件 + 自建语音面（推荐）

1. **对讲 MVP（2–3 周）**
   - 固件：基于灵矽 SDK 或 xiaozhi 固件增加"对讲模式"，按住 PTT 采集 Opus 发往转发服务，收到即播放。
   - 服务端：Go / Node 转发服务，WebSocket（或 MQTT 信令 + UDP 语音），实现房间、抢麦锁、群内转发。
   - 固定频道跑通，2–5 台设备实测延迟与弱网表现。
2. **接入灵矽智能体（2 周）**
   - 实现上述 MCP 工具，挂到灵矽智能体，提示词调成"对讲助手"风格。
   - 设备端音频仲裁：短按 / 唤醒词 → AI 模式；长按 PTT → 对讲；对讲来音优先播放。
   - 切群流程：语音指令 → 灵矽 → MCP → 后端更新设备房间 → 下发设备切换订阅。
3. **建群入口与管理端（2 周）**
   - 小程序 / H5：扫码建群、绑定设备、车队后台。
   - 附近群（GPS 上报 + Redis GEO 等空间索引）、路线群。
4. **AI 增值（持续迭代）**
   - 发言存档、转文字、关键词预警、错过摘要、回放。
   - 紧急频道、车队长优先级、统计报表（B 端收费）。

### 技术要点

- **编码**：Opus 16kHz、60ms 帧，与 xiaozhi 生态一致，ESP32-S3 可承载。
- **弱网**：4G 下 UDP + 抖动缓冲，断线重连并补收。
- **扩展**：初期单机转发；规模上来后按房间分片，或评估七牛 RTC（ESP32 上 WebRTC 偏重，自定义协议更合适）。
- **合规**：录音存档需用户知情；车载设备量产前确认无线电 / 通信相关资质。
